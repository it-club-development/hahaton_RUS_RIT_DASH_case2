# Мотив · исправленная версия v2.0

## Запуск через Docker Compose

Нужны Docker Desktop в режиме Linux-контейнеров или Docker Engine с Compose v2.
Для первого запуска нужен доступ к реестрам образов, npm и NuGet.
React собирается в Docker и отдаётся тем же ASP.NET Core, который обслуживает API.

Из корня проекта рядом с compose.yaml подготовьте файл .env. Если он уже существует,
используйте его и сохраните пароли действующей базы. Для новой установки в PowerShell:

```powershell
Copy-Item .env.example .env
notepad .env
```

В .env заполните WEBOTCHET_DB_PASSWORD, WEBOTCHET_DB_ROOT_PASSWORD и WEBOTCHET_ADMIN_PASSWORD
разными паролями длиной от 12 символов. WEBOTCHET_DB_PASSWORD используется приложением для входа
в MariaDB под пользователем webotchet. WEBOTCHET_DB_ROOT_PASSWORD используется для MariaDB root.
Для паролей MariaDB используйте латинские буквы, цифры, дефис или подчёркивание.
Остановите прежний локальный сервер через Ctrl+C, чтобы освободить порт 5126.

```sh
docker compose up -d --build
docker compose logs -f app
```

Дождитесь строки Now listening on. Адрес в браузере — http://localhost:5126/.
При первой инициализации создаётся администратор из .env, обычно с логином admin.
При существующей базе используется действующий пароль аккаунта.
Ctrl+C в окне просмотра логов завершает только просмотр. Команда docker compose stop
останавливает приложение и БД. Для запуска после изменения исходников повторите
docker compose up -d --build.

Compose ждёт готовности MariaDB. Затем приложение применяет миграции и запускает HTTP.
8080 — внутренний порт приложения, 5126 — порт хоста по умолчанию. Если он занят,
задайте WEBOTCHET_APP_PORT в .env. MariaDB доступна контейнеру по адресу db:3306.
HTTP опубликован только на localhost. Контейнер сохраняет ключи сессий в томе app-keys.
Сценарии start-local.ps1 и start-local.sh оставлены для запуска API на хосте.

## Существующая база

Перед обновлением сохраните резервную копию. Числовые значения в исправленной версии: 0 — администратор, 1 — инженер, 2 — дежурный. Для базы из версий до исходной v1.2, где 1 уже означало «инженер», перенос ролей не нужен.

Если исходная v1.2 уже создавала пользователей или меняла роли, проверьте назначение всех затронутых учётных записей перед запуском исправленной сборки. В исходной v1.2 число 1 означало дежурного, а 2 — инженера. Для базы, которую обновляли с прежних версий, рядом могут находиться записи с разным происхождением. В остановленном приложении действующие роли сверяют по учётным записям и меняют адресно, по идентификатору. Пароли и хеши для сверки не нужны.

```sql
SELECT ID, USERNAME, ROLE FROM USERS ORDER BY USERNAME;
-- После проверки роли конкретного пользователя:
UPDATE USERS SET ROLE = 2 WHERE ID = '<UUID подтверждённого дежурного>';
UPDATE USERS SET ROLE = 1 WHERE ID = '<UUID подтверждённого инженера>';
```

Оставьте администраторам значение 0. Не применяйте массовый обмен 1 и 2 к смешанной базе.

Если том MariaDB уже создан, переменная WEBOTCHET_DB_ROOT_PASSWORD задаёт пароль
при инициализации нового тома. Для действующего тома остановите приложение, сделайте
резервную копию и подключитесь под root с прежним паролем:

```sh
docker compose stop app
docker compose exec db mysql -u root -p
```

В MariaDB запросите список root-учётных записей и смените пароль для каждой фактически
используемой учётной записи с её значением Host. Пример для localhost:

```sql
SELECT User, Host FROM mysql.user WHERE User = 'root';
SET PASSWORD FOR 'root'@'localhost' = PASSWORD('<новый_пароль_root>');
```

Проверьте новый пароль открытием второго подключения. В .env задайте этот пароль в
WEBOTCHET_DB_ROOT_PASSWORD и запустите Compose. Действующий пароль webotchet в .env должен
совпадать с паролем webotchet в MariaDB.

Миграция AlignIncidentStorage допускает повторный запуск после прерывания между DDL-командами.
Для миграций более ранних версий проверяйте схему и журнал миграций на копии базы.

Миграция автора допускает NULL для исторических аварий. Если прежний запуск уже прервался внутри миграции, сначала проверьте состояние схемы по резервной копии и журналу миграций. Новая сборка не удаляет частично созданные объекты автоматически.

## Поведение приложения

- Дежурный создаёт аварии, может менять или удалять свои и закрывать любую открытую аварию. Администратор управляет всеми записями, включая записи без автора. Инженер просматривает отчёт.
- Редактирование сохраняет автора. Чужая запись возвращает 403, отсутствующая — 404. Удаление пользователя, связанного с авариями, возвращает 409 и сохраняет историю.
- При смене роли, имени или удалении аккаунта прежняя cookie отклоняется при следующем запросе. После сброса или смены пароля все ранее открытые сессии аккаунта отклоняются при следующем запросе. После обновления с исходной v2.0 войдите заново.
- В интерфейсе доступны управление пользователями, смена и сброс пароля, темы и подтверждение удаления.

В отчёте сервер применяет фильтры и сортировку, а таблица загружает по 20 аварий. Кнопка «Ещё» расширяет текущую страницу. Сводки по статусу и простою, а также CSV охватывают все подходящие аварии.

Архив содержит шаблон настроек. Если исходный архив с действующими паролями уже был передан другим людям, смените эти пароли отдельно.

## Проверка после запуска

Проверьте обновление на копии базы с историческими авариями. Войдите администратором, инженером и двумя разными дежурными. Проверьте создание дежурным, редактирование собственной аварии, отказ на чужой и сохранение автора при редактировании администратором. Проверьте запрос к отсутствующей аварии, удаление автора с историей, смену роли при активной сессии и запрос обновления пользователя без поля role.

## Работа с карточками и поиск пользователей

- Дежурный или администратор нажимает «Закрыть аварию» в строке отчёта и подтверждает действие. Сервер устанавливает текущее время окончания. Повторное открытие по-прежнему выполняется через карточку с правами редактирования.
- Инженер выбирает «Просмотреть» в строке отчёта. Карточка открывается в режиме чтения.
- В разделе «Пользователи» перед сбросом пароля можно отфильтровать учётные записи по логину или русскому названию роли. Роль показана в скобках рядом с логином.

## MariaDB 10.1 и перенос данных

MariaDB 10.1.48 сохраняет данные в томе mariadb-10-1-data.
Для существующей базы 10.1 запускайте Compose из той же папки проекта или укажите
прежнее имя проекта через docker compose -p ИМЯ. Проверьте название тома через
docker volume ls. Не используйте docker compose down -v для обновления. При запуске нового
контейнера не оставляйте прежний ASP.NET Core работающим с той же базой.
Часовой пояс контейнера задаётся WEBOTCHET_TZ, по умолчанию Asia/Yekaterinburg.
Для одинаковой интерпретации времени установите тот же пояс на рабочих местах.

При переходе с MariaDB 12.3 требуется логический перенос. Не подключайте старый том к MariaDB 10.1. Остановите приложение и сохраните резервную копию. Экспортируйте только данные и схему приложения webotchet. Откройте новую базу в отдельном томе, проверьте совместимость SQL-дампа с 10.1 и загрузите его до первого запуска приложения. При загрузке сохраните таблицу __EFMigrationsHistory, чтобы применились только недостающие миграции. Пробный перенос выполняйте на копии. Для новой пустой базы достаточно .env.example и сценария запуска.

Драйвер Doka использует явный режим AllowUnsupported, потому что MariaDB 10.1 находится за пределами его матрицы поддержки. Для нулевой даты настроен режим SQL без NO_ZERO_DATE и чтение ConvertZeroDateTime. При приёмке проверьте создание открытой аварии, повторное открытие и закрытие, прямым SELECT проверьте END_TIME и повторите проверку на восстановленной копии базы.

## Расчёты и права

Для НВ база хранит 0000-00-00 00:00:00, API отдаёт null. Сервер и фронтенд вычитают время начала из текущего времени и ограничивают результат снизу нулём. Открытая строка пересчитывается раз в секунду. Для закрытой записи используется фактическое время окончания. Дата и время интерпретируются как локальные. Для одинаковых значений настройте один часовой пояс на хосте приложения и рабочих местах.

NUMB_RBS хранится как INT. Значения 1–10000 означают количество БС. Значение 0 зарезервировано для сектора «С», а числовой ввод 0 отклоняется. Для «С» простой остаётся неопределённым до согласования правила. COMMON_PROSTOY имеет тип TIME и автоматически заполняется для значений в пределах ±838:59:59. Для больших значений TIME остаётся NULL. Точный простой в секундах хранится в служебном COMMON_PROSTOY_SECONDS (BIGINT) и используется в API, сводках и CSV. KATEG имеет тип TINYINT. Миграция сохраняет ранее рассчитанные значения, включая значения выше предела TIME. Откат выполняется из резервной копии.

| Действие | Администратор | Дежурный | Инженер |
|---|---|---|---|
| Читать отчёт, карточки и CSV | Да | Да | Да |
| Создать аварию | Да | Да | Нет |
| Изменить, открыть снова или удалить | Любую | Свою | Нет |
| Закрыть открытую аварию | Любую | Любую | Нет |
| Управлять чужими учётными записями | Да | Нет | Нет |
